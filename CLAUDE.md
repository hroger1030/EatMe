## Projects

- `EatMeClient` — MonoGame client (namespace `EatMeClient`). Content assets are built from `Content/Content.mgcb`. Music lives in `Content/music` (MP3s, `Mp3Importer` + `SongProcessor`). Sound effects are WAVs in `Content/audio` (`WavImporter` + `SoundEffectProcessor`), named in the library's `Const - Audio.cs` as `SFX_*`; Sounds are either global (heard everywhere in the level at full volume) or local (falling off in volume with distance from the listener, the camera on the own pac). UI sounds play through `SoundManager.PlaySound(name)`, in-world ones through `SoundManager.PlaySound(name, volume)` with the volume from `SoundMath.GetEventVolume` (library): global events (`SoundMath.IsGlobalEvent`: flag captured, lost, returned and about to win) play at full volume, and the rest fade in a straight line from the board's centre (the camera, on the own pac) to silent at the board's edge and beyond (`SoundMath.GetOnScreenVolume`), so nothing off screen is heard. Announcer voice clips are `Content/audio/SoundFX_Msg_*.wav` (`Const.SFX_MSG_*`; how they were made, step by step, is in README.md): `Announcements.GetSound(eventType, team)` (library) picks one for a `GameEventMessage` from its `EventType` and `Team`, and `MultiPlayerGameScreen.PlayEventSound` queues it to play to everyone at full volume, wherever the event happened. Global sounds never overlap: announcer clips (and the `SFX_FLAG_CAP` sting just before a capture's clip) go into an `AnnouncementQueue` (library) and `MultiPlayerGameScreen.UpdateAnnouncements` plays them one at a time on a single `SoundEffectInstance` (`_Announcer`), starting the next only when the last has finished; a clip already waiting isn't queued twice, and one that has waited over `AnnouncementQueue.MAX_WAIT_MS` (3 s) is dropped. The level end fanfare clears the queue and cuts off any clip playing, and quitting clears it too. `Const.SFX_TICK` (`SoundFX_Tic1`) is the UI tick: `TypingTextControl` plays it for each visible character typed, every menu plays it when the selection moves up or down by keyboard or gamepad, left and right play it on toggles and sliders (once per press, not while held), the Join Game name box (`TextInputControl.PlayTypingSound`) plays it for every key typed, backspace included, and every mouse click on a menu item, toggle, slider or Back plays it. Mouse hover never does. Plain text files (e.g. `Content/Text/story.txt`, shown by the story screen) are added with `/copy:` and loaded with `AssetCache.LoadTexts`, which converts curly quotes and dashes to ASCII because sprite fonts are built with printable ASCII only. All content source files must live inside `Content/`. The UI font is JLS Space Gothic (`Content/fonts/JLSSpaceGothic-CNC.otf`, freeware, non-commercial use only), built at five sizes: `Content/fonts/JLSSpaceGothic96.spritefont` (`Const.FONT_JLSSPACEGOTHIC96`) for screen titles, `JLSSpaceGothic60` (`FONT_JLSSPACEGOTHIC60`) for the rest of the text on the menu screens, `JLSSpaceGothic48` (`FONT_JLSSPACEGOTHIC48`) for the game screen, the title scroller and the version label, `JLSSpaceGothic36` (`FONT_JLSSPACEGOTHIC36`) for the story text, and `JLSSpaceGothic30` (`FONT_JLSSPACEGOTHIC30`) for the high score table and the in-game player state panel. Text is never drawn scaled; a new size is a new sprite font. Player names are drawn below each pac in Arial Bold through `Content/fonts/Arial20.spritefont` (`Const.FONT_ARIAL20`); it names the installed system font rather than a `.ttf` in `Content/` (Arial can't be redistributed), so the content build needs Arial installed. Content names and UI strings go in `Const` in `EatMeLibrary/Objects/Const` (namespace `EatMeLibrary`, so server and client share them); only MonoGame colors stay in the client, in `ClientColors`, since the library has no MonoGame dependency. Content is loaded up front in `TitleScreen.LoadAllAssets`. Images live in `Content/images` and use `TextureProcessor` with mipmaps off and `TextureFormat=Color`; draw pixel art with `SamplerState.PointClamp`. `Const.IMAGE_TITLE_BACKGROUND` is the background for the title menu and every other menu screen (not the game), drawn by `TitleScreen.Draw` before the active screen and scaled to cover the screen by `TitleScreen.GetCoverRectangle`. Menu text on those screens is drawn straight onto the background in the dark menu colors (`ClientColors.COLOR_DARK_MENU_*`: item, selected, heading, hint and the slider track backgrounds, plus `COLOR_DARK_TITLE_ITEM`, near black, for screen titles and section titles such as "LAN Games"); the in-game menu, over the dark board, uses the light ones (`COLOR_LIGHT_MENU_*`: item, selected, panel). Every menu color comes from those constants, so change them there. The story text still sits on a `ClientColors.COLOR_TEXT_PANEL` panel (half-transparent black). The title is the `Const.IMAGE_LOGO` image (magenta 255,0,255 is color-keyed to transparent), half the screen wide and centred a quarter of the way down. Across the bottom of the title menu (only there, not its sub-screens) the `MessageScroller` control scrolls `Const.STRING_TITLE_SCROLLER` (until a server has sent its message of the day: when a game returns to the title, `TitleScreen.ReturnFromGame` shows `MultiPlayerGameScreen.MessageOfTheDay`, from `ClientGameState.MessageOfTheDay`, instead) right to left in yellow JLS Space Gothic on a black bar; `ScrollerMath.GetTextX` (library) gives the text's position, starting off the right edge and starting over once it has left the screen. The `VersionLabel` control draws the client version (`VersionLabelMath.GetVersionText(NetworkConstants.APP_VERSION)`, library, e.g. "v0.9") in `COLOR_DARK_TITLE_ITEM` JLS Space Gothic in the top right corner of the title menu and every other menu screen (not the game), drawn by `TitleScreen.DrawScreens` right after the background; `VersionLabelMath.GetTextX` places it. The title theme (`Const.SONG_TITLE_THEME`) loops on the title and its menus and stops when a game starts. Level music is a playlist, not part of `Levels`: `TitleScreen.LoadAllAssets` scans the built `Content/Music` folder for `Track*.xnb`, `MusicPlaylist.GetTrackNames` (library) orders them (`TrackN` by number, then every `TrackNb` by number) into `MusicManager.LevelTracks`, and they are loaded up front with the title theme. On `LevelStartMessage` `MusicManager.PlayLevelTrack` plays track `MusicPlaylist.GetTrackForLevel(level, count)`, one per level, starting over after the last; no tracks means silent levels. To add a track, put `TrackN.mp3` (or `TrackNb.mp3`) in `Content/music` and `Content.mgcb`; nothing in code names it. Every frame is drawn into a `RenderTarget2D` (`TitleScreen.GetSceneTarget`, remade when the back buffer changes size) and copied to the screen through the `Content/effects/Brightness.fx` shader (`Const.EFFECT_BRIGHTNESS`, `EffectImporter` + `EffectProcessor`, loaded with `AssetCache.LoadEffects`) by `TitleScreen.DrawWithBrightness`, so the player's `GameSettings.Brightness` (percent, 50 to 100, default 100) dims everything. Its limits and the shader's maths (`DisplayAdjust.AdjustColor`, kept in step with the `.fx`) are in `DisplayAdjust` (library); `ConfigManager.Load` clamps a loaded value back into range. The settings screen's Brightness fader is a `SliderControl` like the volume ones and is applied live. Every setting on the settings screen is one line (`SliderControl.IsInline`: label, track, then the value in a fixed-width column; the Controls toggle with `ToggleControl.IsInline`), with the labels right-aligned in a shared column (`LabelWidth`) and the block centred as a whole. Before that pass, if `GameSettings.Bloom` (percent, 0 to 100, default 0 meaning off) is above 0, `TitleScreen.DrawBloom` makes a glow from the frame with `Content/effects/Bloom.fx` (`Const.EFFECT_BLOOM`): technique `BrightPass` keeps each channel's excess over `DisplayAdjust.BLOOM_THRESHOLD` into a half size target, then technique `Blur` blurs it `BLOOM_BLUR_PASSES` times each way with `DisplayAdjust.GetBlurWeights`, and `DrawWithBrightness` adds it over the frame (one-plus-one blend, tinted by `DisplayAdjust.GetBloomIntensity`), so bloom applies to every screen and brightness still dims the result. Its limits and maths (`ClampBloom`, `ApplyBloomThreshold`, kept in step with the `.fx`) are in `DisplayAdjust`; `ConfigManager.Load` clamps it, and the settings screen's Color Bloom fader (`Const.STRING_BLOOM`) is applied live. Only one client runs at a time per Windows login: `Program.cs` takes the named mutex `Const.CLIENT_INSTANCE_MUTEX_NAME` (`Local\EatMeClient`) and a second copy exits silently before opening a window. Typed text arrives through `Window.TextInput` into `InputManager.TypedCharacters` (backspace is `''`); `TextInputControl` uses it for text boxes. Screens with text boxes navigate with the arrow keys only, since W and S may be typed. In a game, Esc (or the gamepad's Back) opens the `InGameMenu` (Resume Game, Game Settings, Quit Game) (its panel filled with rounded corners, `TextureHelper.FillRounded`, `MiniMap.CORNER_RADIUS`) and sets `GameSettings.Paused`; the client stays connected and `ReceiveMessages` keeps applying everything the server sends. Game Settings opens `MultiPlayerGameScreen`'s own `SettingsScreen` over the title background, hiding the game; its Back (or Esc) returns to the in-game menu, and `TitleScreen` keeps `IsMouseVisible` in step with the Controls setting during a game. While paused the game is silent (`MultiPlayerGameScreen.PauseGame`): music pauses, loops and announcements stop, and event sounds, announcer clips and the level end fanfare are skipped rather than queued; only the menus' `SFX_TICK` plays. A `LevelStartMessage` while paused doesn't start its track; on resume `MusicPlaylist.GetResumeMusic` (library) says whether to resume the paused track, start the current level's track, or stay silent during the results.
- `EatMeLibrary` — class library (namespace `EatMeLibrary`) referenced by both client and server. Put code shared between them here. No MonoGame dependency, since the server is headless. Colors in the library are `FastColor` (one `uint`, `PackedValue`, in MonoGame's `Color` layout 0xAABBGGRR so `ClientColors.ToColor` and `ToFastColor` are straight copies; built with `FromArgb(a, r, g, b)` or `FromRgb(r, g, b)` from bytes, read back with `R`/`G`/`B`/`A`; `NetworkHelper.WriteColor` sends it as a `uint`), not `System.Drawing.Color`; the client converts with `ClientColors.ToColor` and `ToFastColor`.
- `EatMeTests` — NUnit tests (namespace `EatMeTests`) for public functions, mainly in `EatMeLibrary`.
- `EatMeServer` — headless console server (namespace `EatMeServer`). On startup `ConfigManager.Load()` reads `server.cfg` (JSON) from the output directory into `ServerSettings`; a missing or invalid file is fatal (exit code 1). Every server.cfg setting but Port and DiscoveryPort has its own explicit console command in `SettingCommands` (its name in lower case, e.g. `pacspeed 7.5`; alone it shows the value): a constant, a `COMMANDS` row (listed by `help` under Settings), a case in `SettingCommands.Execute` and a row in `GetSettingRows` (the `settings` command). MinPlayers, AutoBalanceTeams and MessageOfTheDay are `bots`, `autobalance` and `motd` in `ServerCommands`. A new server setting needs all four (no reflection). A changed value goes through `ConfigManager.Normalize` (shared with `Load`: MazeSize must be valid or the old value stays, the rest clamp); a GameConfig change then calls `GameServer.SendGameConfig`, which broadcasts a `GameConfigMessage`, and `maxplayers` rebalances bots. All server console output goes through `ServerLog.Write(eLogType, text)`, which colors each line by its `eLogType` (`ServerLog.GetColor`: Info grey, Level magenta, Join green, Leave dark yellow, Kill dark red, Flag cyan, PowerUp blue, Command output white, Warning yellow, Error red, to standard error); never call `Console.WriteLine` directly in the server. Once `Program.cs` calls `ServerLog.EnablePrompt` (with a stopwatch started at launch) the console's last line is always the typing prompt `[Up:h:mm] ` (`ServerLog.GetPrompt`): `Write` ends the prompt's line first and shows it again after, the command reader calls `OnLineTyped` (Enter ended the line), a command with no output calls `ShowPrompt`, and `DisablePrompt` runs before "Server stopped.". The map settings (`GameConfiguration.MAP_SETTINGS`) only count from the next level: `GameServer` keeps `_LevelConfig` from `StartLevel`, and `BuildClientConfig` (sent in `WelcomeMessage` and every `GameConfigMessage`) keeps the level's map settings, so clients build the map the server is playing; `StartLevel` broadcasts a `GameConfigMessage` before the `LevelStartMessage` when they changed. `Program.cs` reads TickRate every tick. Document new commands in `ServerCommands.COMMANDS` (help), README.md and Specs.md. New server settings go in both `ServerSettings.cs` and `server.cfg`. `ServerSettings.StartingLevel` (server.cfg, default 1) is the level the server starts on, passed by `Program.cs` to the `GameServer` constructor; `ConfigManager.Load` raises anything below 1 to 1 (`ConfigManager.ClampStartingLevel`), and there is no upper limit since past the last level the list starts over. Game rule settings live in `EatMeLibrary.GameConfiguration` and appear under the `GameConfig` block in `server.cfg`; add new ones to both. `server.cfg` lists every setting at its default value, so keep it in sync when defaults change. `ServerSettings.MessageOfTheDay` (server.cfg) is sent to every joining player in `WelcomeMessage.MessageOfTheDay`; empty or missing means `Const.MOTD_DEFAULT` (`ConfigManager.GetMessageOfTheDay`, applied by `ConfigManager.Load` and again when the welcome is built). `LoadingScreenTipsManager.Load()` reads every line of `LoadingScreenTips.txt` (copied to the output directory, no line limit); each joining player gets every line in `WelcomeMessage.LoadingScreenTips` (kept in `ClientGameState.LoadingScreenTips`), and on each `LevelWonMessage` the client picks one at random (`TipRules.PickTip`, library) into `ClientGameState.IntermissionTip`, which `DrawResults` shows at the bottom centre of the results in Arial20, in quotes and straight onto the picture (no panel), under "Next Level in n". A missing file just means no messages. `BotNameManager.Load()` reads `bot_names.txt` the same way; bot names skip `PlayerNameRules`. `HighScoreManager.Load()` reads `highscores.txt` (copied to the output directory) into `HighScoreManager.Scores` (`HighScoreEntry`, shared in the library), one `Name,Score,Date` per line (the name may hold commas), ranked highest first by `HighScoreRules.Parse` (library, with `Format`, `Rank`, `Submit` and `Merge`, shared with the client); blank lines are skipped, bad lines are logged and skipped, and a missing file just means no high scores. Typed console commands: a background thread in `Program.cs` reads `Console.ReadLine` into a queue that the main loop drains (after network events) into `ServerCommands.Execute(game, line, out quit)`, so they touch the game on the main thread only. `ServerCommands.Parse` turns a line into a command from `ServerCommands.COMMANDS` (name, usage, help text; two word commands such as `next level` win over one word ones) or `ALIASES`, plus the rest of the line. The commands (listed in Specs.md) use public `GameServer` calls: `StartLevel`, `FindPlayers` (id or name, ignoring case), `Kick` (humans only: a `RejectMessage` with `eRejectReason.Kicked`, shown by the client as `Const.STRING_REJECT_KICKED`, then `Remove` and `BalanceBots`), `SetMinPlayers` (clamped to 0 to `MaxPlayers`; `add bot`/`remove bot` change it by n, or 2n with `AutoBalanceTeams`, from the current player count, since every join and leave rebalances bots to it) and `SetAutoBalanceTeams`; `motd` sets `Settings.MessageOfTheDay`. Nothing is written back to `server.cfg`. To add a command, add a constant and a `COMMANDS` row and handle it in `Execute`. There is no ban list. `GameServer` is given that list and `HighScoreManager.Save` as `onHighScoresChanged`; when a level is won, `GameServer.UpdateHighScores` puts every human's `Player.TotalScore` (points won since connecting, never reset) on it if it makes the top `HighScoreRules.MAX_HIGH_SCORES` (100) through `HighScoreRules.Submit`. Bots and players with no points are left off, and each connection has one entry (`ServerPlayer.HighScore`) that is updated rather than added again. Whenever the list changes the server also broadcasts a `HighScoresMessage` (built by `GameServer.BuildHighScores`), and sends one to each player right after `WelcomeMessage`; the client keeps it in `ClientGameState.HighScores` and `MultiPlayerGameScreen` merges it into the client's own list, `HighScoreStore` (client, loaded in `TitleScreen.LoadContent`, saved to the client's `highscores.txt` next to its exe whenever it changes) through `HighScoreRules.Merge`: the top `MAX_HIGH_SCORES` from every server the client has played on, one entry per name per date (a same name and date entry only raises the score), so a kept score only drops off when higher ones push it out. `HighScoresScreen` shows that list (empty means only its title and Back): the 30 size font, ranks as `1)` (`HighScoreRules.GetRankText`), two side by side columns each with its own headings, entries running left to right then down (`GetRowCount`, `GetEntryIndex`), and the rows clipped between the headings and Back, scrolled by the mouse wheel, Up/Down/W/S, the d-pad, PageUp/PageDown, Home/End or dragging the scrollbar (`ScrollMath`, library); left and right select Back. The file is rewritten only when the list changes; a build doesn't overwrite it unless the source `highscores.txt` is newer.

## Maps

- `MapMaker.Generate(config, seed)` in `EatMeLibrary` builds the level as an `eGridDef[,]` (`[x, y]`, square, `MazeSize` wide). Each cell is either `Wall` or open, plus item flags. The same config and seed always give the same map.
- `MazeSize` must be even and at least `MapMaker.MIN_MAZE_SIZE` (18), so the halves meet on the line between the two middle columns and there is no center column to handle. `MapMaker.ValidateMazeSize` throws `ArgumentOutOfRangeException` otherwise; `Generate` calls it, and so does the server's `ConfigManager.Load`, so a bad `server.cfg` stops the server at startup. The maze's cell grid (`ToCells`) is always odd, and `Expand` makes it one cell bigger by duplicating the center row and column. Don't add code for odd map sizes.
- Only the left half is generated; the right half is built from it (see Maps in Specs.md). Every room carved into the cell map is copied with `MapMaker.GetCopy`.
- `Generate` runs: 1) the maze (`Maze.AddWalls`, `ToCells`, `Expand`), 2) `AddRandomRooms`, 3) `AddOuterWall`, 4) `OpenWarpTunnels`, 5) the special rooms (`AddGhostPen`, `AddFlagRooms`, `AddSpawnRooms`), then `RemoveSmallWalls`, `PlaceItems` and `AddPowerUpSpawns`.
- `AddPowerUpSpawns` flags two cells on the left half `eGridDef.PowerUpSpawn` (the plain `Food`-only cells outside the ghost pen nearest its centre, one above its middle row and one below) and their copies, so every map has four. It uses no randomness. They keep their dot and are drawn as normal cells.
- The ghost generator is a 2x2 block of `GhostGenerator` cells in the map center. `PlaceItems` places its left part and copies it like every other item.
- `MapMaker.Maze` starts as a fully open grid of rooms and `AddWalls` closes passages and fills rooms until `MapMaker.MAZE_JUNCTION_PERCENT` of open cells are junctions. Every change is undone unless the maze stays valid: no dead ends, every open cell reachable, and at least `Maze.MIN_CENTER_CROSSINGS` passages between the halves. `MAZE_JUNCTION_PERCENT` is a constant, not a `GameConfiguration` setting, because clients must build the same map as the server.
- Random rooms (`AddRandomRooms`): 0 to `MAX_RANDOM_ROOMS` (4) per side, each `MIN_ROOM_SIZE` to `MAX_ROOM_SIZE` (2 to 5) cells wide and high, in the left half off the outer ring, and only where they touch an open cell (`TouchesOpen`). Rooms are at least 2x2 so no carved cell can be a dead end; carving only opens cells, so reachability holds.
- Special rooms are carved with `MapMaker.AddRoom` (`CarveRoom`, then `ConnectRoom` digs a passage to the nearest open cell if the room touched none). They are kept in a `reserved` list and placed with `IsClear`: flag rooms (`MIN_FLAG_ROOM_SIZE` to `MAX_FLAG_ROOM_SIZE`, 3 to 5 cells a side, back quarter of the left half) may not overlap anything reserved; spawn rooms (`SPAWN_ROOM_SIZE`, 3x3 `SpawnPointRed`/`SpawnPointBlue` cells, `PlayerBaseCount` per team) keep a one-cell gap, so no flag base is within 3 cells of a spawn tile. The ghost pen is the generator plus one cell all round (4x4). The flag base goes on the room's centre cell. `MapMaker.MIN_MAZE_SIZE` (18) is the smallest map that fits the pen and the flag rooms.
- `RemoveSmallWalls` opens any wall not joined to the outer wall with fewer than `MIN_WALL_CELLS` (3) cells, so carving leaves no lone pillars or stubs.
- Clients build their own copy of the map, so a change to the map built from a seed only works between a client and server of the same `NetworkConstants.APP_VERSION`. `MapMakerTests` check symmetry, dead ends, reachability and junction share.
- `MapMaker.Print(map)` returns an ASCII rendering for debugging.
- Wall color, wall fill color and background color are not map data; the server sends all three in `LevelStartMessage`. Each level's `LevelInfo.BackgroundColor` is a dark color: a darker shade of its wall color, its complement, or something else, from black up to clear deep tints (`LevelsTests` keeps every channel at 96 or below), and `MultiPlayerGameScreen.Draw` fills the board with it (`ClientGameState.BackgroundColor`) before the maze. A level with `LevelInfo.BackgroundImage` set (only Pac Paradise, `Const.IMAGE_SPACE_FILL`, `Content/images/SpaceFill (256x256x1).png`, a starfield) has it tiled over the background color by `DrawBackgroundImage`, fixed to the world so it scrolls with the maze, only the tiles on screen; the client takes it from `Levels`, so it isn't sent. Each level's `LevelInfo.WallFillColor` (a darker shade of the wall color that fits the level's name) fills the inside of the walls; `FastColor.TRANSPARENT` (alpha 0, Pac Paradise) means hollow walls and draws nothing, so the starfield shows through.

## Levels

- `Levels.GetLevel(level)` in `EatMeLibrary` returns a `LevelInfo` for a level number starting at 1. The rules for levels are in Specs.md.
- Bonus items are `ePowerUp` flags (a `long`, one bit per item, `Any` is all of them). Power pills aren't in `ePowerUp`, since every level has them. Each level introduces exactly one item no earlier level has (listed first in its set), and later levels bring back earlier ones; `LevelsTests` checks this, so a new item needs a new level (or must replace one) and must be added to `Any`. Projectiles and objects that effects put in the maze have their own sheet, `Const.IMAGE_WEAPON_EFFECTS` (`Content/images/WeaponEffects(60x60x20).png`, magenta keyed out, loaded up front, drawn in their own colors, not tinted): one row per `eWeaponEffect` (BFG shot, banana peel, sword, holy flame, blue shell, tetris block, poke ball, hammer, fireball, spread shot) in enum order, two 60x60 animation frames each, left to right, each shown `FRAME_SECONDS` (0.25); `WeaponEffectSprites` (library) gives `GetCellX(frame)`, `GetCellY(effect)` and `GetFrame(seconds)` (`FRAME_SECONDS` a frame), so a new one is a new row and enum value. Bonus item sprites are on one sheet, `Const.IMAGE_POWER_UP_SHEET` (`Content/images/powerups(60x60x32).png`, magenta keyed out, loaded up front): one 60x60 cell per flag in bit order, eight to a row, so a new item's sprite goes in the next cell; `PowerUpSprites.GetCellIndex`, `GetCellX` and `GetCellY` (library) find an item's cell. `MultiPlayerGameScreen.DrawPowerUps` draws them (see Power ups under Networking).
- Add or change levels in the `LEVELS` table in `Levels.cs`.
- A level with `LevelInfo.IsRainbow` (only level 32, Pac Paradise) is a rainbow level; the colors are `Rainbow` (library). Its dots are `Rainbow.BuildDotColors` (seven `Rainbow.COLORS` in diagonal stripes, `(x + y) % 7`), used by `ClientGameState` on `LevelStartMessage` instead of the team halves. `DrawWall` tints each wall quarter `Rainbow.GetWallColor` (the smooth `GetGradientColor` along the same diagonal, a cell's centre matching its dot) instead of the wall color. Ghosts are `PacRules.RAINBOW_GHOST_SCALE` (2) times as big for both drawing and contact (`PacRules.GetGhostRadius(isRainbow)`, passed to `IsTouchingGhost` by `GameServer.ResolveGhostContacts`), and drawn from one of `RAINBOW_GHOST_PHASES` (16) sheets built at load by `ImageFactory.GenerateRainbowGhostSheet` (`Rainbow.ReplaceWithGradient`: the white body as a left to right gradient, moved round by a phase); `Rainbow.GetScrollPhase(x, y)` picks the sheet from the ghost's position, so the rainbow scrolls once every `GHOST_SCROLL_CELLS` cells moved.- Eaten dots don't regrow on a timer. `DotRegenQueue` (library) is a FIFO of `EatenCell` structs (`ushort X, Y`) over a `Queue<EatenCell>`, so eating allocates nothing (`Reset` calls `EnsureCapacity` for the level's dot count). `GameServer.EatDot` clears the dot and calls `DotRegenQueue.Add`; once the queue holds `Threshold` cells (`GameConfig.DotRegenPercent`, 0 to 100, default 50, of the level's dots, from `DotRegenQueue.GetThreshold`) each dot eaten puts the oldest eaten one back, so that share stays eaten. `StartLevel` resets it with `GameServer.CountDots`; `ConfigManager.Load` clamps the percent. `GameServer.EatenDots` exposes it, and `BuildEatenCells` lists its cells for late joiners. Power pills keep their countdown (`CellRegen`, `GameConfig.PowerPillRegenTimeMs`, `UpdateRegens`).

## Networking

- How the client and server split the work is in Specs.md. Default ports are in `NetworkConstants` (game 7777, discovery 7778).
- Messages live in `EatMeLibrary/Objects/Network/Messages`, one class per message, each implementing `INetworkMessage` with matching `Write`/`Read` methods. Every message has a value in `eMessageType` and a case in `MessageSerializer.CreateMessage`.
- A frame on the wire is `[int32 body length][message type byte][fields]`. `MessageSerializer.Serialize` builds a frame; `FrameBuffer` turns received bytes back into whole messages. Corrupt data throws `InvalidDataException`, and the connection should be dropped.
- Clients build the map from the `GameConfiguration` in `WelcomeMessage` and the level number in `LevelStartMessage`, then apply `CellsChangedMessage` updates. A level's map seed is `Levels.GetSeed(GameConfiguration.ServerSeed, level)` (server seed plus level number); levels have no seed of their own, and the seed is never sent on its own. The server also seeds its level `Random` with it.
- New `GameConfiguration` properties must also go in `NetworkHelper.WriteGameConfiguration` and `ReadGameConfiguration`; a unit test fails if one is missed.
- There is no protocol version and never any backwards compatibility: a client and server with the same `NetworkConstants.APP_VERSION` always speak the same messages, so message layouts can change freely between versions.
- `NetworkConstants.APP_VERSION` (float, 0.9) is the game version shared by client and server; the client and server versions need to match. The client sends its version in `HelloMessage.ClientVersion` when it connects, and the server sends its own in `DiscoveryResponseMessage.ServerVersion`; the LAN list shows it after the server name ("Eat Me Server (v0.9)", `ServerListing.GetDisplayName`). `ServerBrowser` lists every server it hears from, whatever its version, but only one with the same `APP_VERSION` can be joined (`ServerListing.CanJoin`): `JoinGameScreen` greys the others out in `COLOR_DARK_MENU_HINT` and shows `Const.STRING_REJECT_VERSION` instead of connecting, and `GameServer.HandleHello` rejects a `HelloMessage` with a different `ClientVersion` (`eRejectReason.VersionMismatch`), which covers addresses typed in by hand.
- `SnapshotMessage` is the game state sent `TargetFps` times a second.
- Server side: `NetworkServer` accepts TCP clients; each `ClientConnection` reads and writes on background tasks and queues `NetworkEvent`s. The main loop in `Program.cs` drains that queue into `GameServer.HandleEvent`, then calls `GameServer.Update`, so game state is only touched on the main thread. `DiscoveryResponder` answers LAN broadcasts on `DiscoveryPort`.
- `GameServer` talks to clients only through `IClientConnection`, so tests drive it with `FakeConnection` (in `EatMeTests`) and no sockets.
- Player positions are in map cells, as floats; a pac in the middle of cell (x, y) is at (x + 0.5, y + 0.5).
- `MessageConnection` (library) is the shared TCP connection: background read and write tasks, a bounded send queue, and `CloseReason` when it drops. The server wraps it in `ClientConnection`; the client uses it through `NetworkClient`.
- Client side: `JoinGameScreen` collects name, preferred team (`eTeamPreference`: Either, the default, Red or Blue; sent in `HelloMessage.PreferredTeam`) and address (saved in `GameSettings`), one line each with the labels right-aligned in a shared column (the name in a box `PlayerNameRules.MAX_LENGTH` average characters wide, `TextInputControl.ShowBox`; the team toggle with `ToggleControl.IsInline`), and lists LAN games from `ServerBrowser`. `MultiPlayerGameScreen` owns a `NetworkClient` and a `ClientGameState`; each frame it applies received messages to the state, sends input only when the held direction changes, and pings every 2 seconds.
- `ClientGameState` (library) holds everything the client knows and has no drawing code, so it is unit tested directly.
- Drawing: a cell is `MultiPlayerGameScreen.CELL_PIXELS` (48) pixels, only cells on screen are drawn, and a pac is drawn `PacRules.GetDiameter(size)` cells wide (one cell at size 0, one more for every `PacRules.SIZE_PER_EXTRA_CELL`). Sprites are white and tinted (team colors for pacs and flags). The player's own pac (body, power pulse, trail, name, death animation and mini map dot) uses a lighter shade of its team color, `ClientColors.COLOR_PAC_RED_OWN` or `COLOR_PAC_BLUE_OWN`, picked by `ClientColors.GetPacColor(team, isOwn)`, so it stands out in a crowd; this is client side only. Ghosts instead share one sheet, `Const.IMAGE_GHOST` (white body, black outline, green eyes), recolored once in `MultiPlayerGameScreen.LoadContent` by `ImageFactory.GenerateGhostSheet` into one texture per ghost personality (indexed by `GhostPersonality.Id`, colored `GhostPersonality.Color`); `GhostPalette.ReplaceColor` (library) swaps only pixels exactly `GhostPalette.BODY_COLOR` (pure white), so the outline and eyes keep their colors and the body must stay pure 255,255,255 in the art (so no personality may be pure white). `DrawGhosts` picks each ghost's sheet from `ClientGameState.GetGhostPersonality(ghostId)` and draws its name below it (`DrawName`, Arial20 like pac names) in its color, or in white with the rainbow skin on a rainbow level. `GhostPalette.GetColor` (random seeded colors) is no longer used for drawing. The board's SpriteBatch uses `SamplerState.LinearClamp` with the sharp bilinear `Content/effects/PixelArt.fx` (`Const.EFFECT_PIXEL_ART`), wrapped in `PixelArtEffect`, which sets the shader's `TextureSize` from the texture SpriteBatch binds before each run of sprites; texels stay solid and only the last half screen pixel at each texel edge blends (`PixelArtFilter.GetSampleTexel`, library, mirrors the shader). Everything else (HUD, mini map, menus, results) stays point sampled. `Camera.ToScreenPosition` rounds the camera offset to whole pixels (`CameraMath.GetScreenOffset`, library) so the maze doesn't crawl. Pacs with an effect that `PowerUpEffects.HasSpeedTrail` allows (only `ePowerUpEffect.SugarRush`; not the power pill) leave a speed trail: `PacTrails` (library) keeps each such pac's last `TRAIL_LENGTH` positions, sampled every `TRAIL_SAMPLE_SECONDS` and dropped when it loses the effect, dies or jumps more than `MAX_TRAIL_STEP` cells (warp or respawn), and `DrawPacs` draws a copy at each, fading by `PacTrails.GetAlpha`. Walls are tubes tinted the level's wall color, drawn in quarters cut from the `Const.IMAGE_WALL` tile; `WallTiles.GetQuarter` (library) picks each quarter's piece (outer corner, edge, inner corner, or nothing inside a solid block) and its clockwise quarter turns from the quarter's two side neighbours and the diagonal between them (off the map counts as open). Unless the level's wall fill color is transparent, `DrawWall` first fills each quarter in `ClientGameState.WallFillColor`: the matching quarter of `Const.IMAGE_WALL_FILL` (`Content/images/wallfill.png`, laid out like the wall tile, white from the tube line inward, magenta keyed out) with the same turns, or a solid half cell where `GetQuarter` draws nothing, inside a solid block. Ghost spawn cells (`eGridDef.GhostGenerator`) have the `Const.IMAGE_GHOST_BASE` floor (`GhostBase0.png`) drawn in `COLOR_PAC_YELLOW` under any dot or pill, and spawn tiles have the `Const.IMAGE_PAC_BASE` floor (`Pacbase0.png`) in their team's spawn color (`ClientColors.GetSpawnColor`: a bright rose red for red, a bright sky blue for blue, equally bright so they show up on any background). Flag base cells (`eGridDef.FlagBaseRed`/`FlagBaseBlue`) have the `Const.IMAGE_FLAG_BASE` bullseye drawn under them, blinking between the base team's color and yellow every `FLAG_BASE_BLINK_SECONDS`. Every dot and power pill has its own color, `ClientGameState.DotColors[x, y]`, rebuilt with the map on each `LevelStartMessage` with `ClientGameState.BlueDotColor` on blue's (left) half and `RedDotColor` on red's (right) half (`ClientGameState.BuildDotColors`; set by the client to `ClientColors.COLOR_PAC_DOTS_BLUE` and `COLOR_PAC_DOTS_RED`, light blue and light red; pale enough to read as dots but strong enough to tell apart). Power pills blink on and off every `POWER_PILL_BLINK_SECONDS`. Flags (loose and carried) flicker between yellow and their team color every `FLAG_FLICKER_SECONDS`. A pac with `PacState.Powered` set pulses smoothly between its team color and white (the sprite untinted) every `POWER_PULSE_SECONDS`. When a `GameEventMessage` reports a pac eaten, the death sheet (`Const.IMAGE_PAC_DEATH_SHEET`, 11 frames) plays once at that spot in the pac's team color and size, built by `ImageFactory.GeneratePlayerDeath` and kept in `DeathAnimations`. The game has a black score and message bar across the top (the score font's height plus `HUD_BAR_PADDING` above and below) with "Blue n" on the left, "Red n" on the right and "Level n name" (`ClientGameState.GetLevelTitle`) in the middle; a matching black stats bar across the bottom (`DrawStatsBar`) shows the player's own running total (`PacState.TotalScore`) followed by Flags, Ghosts, Chomps and Rescues on the left (`PacState.FlagCaps`, `GhostKills`, `PlayerKills`, `Rescues`, counted on `Player` by the server and sent in every snapshot), and the ping (`ClientGameState.GetPingText`, from `PingMs`, the round trip of the last Ping/Pong; "Ping --" before the first, in white) on the right, drawn in `ColorRamp.GetPingColor` (library: clamps to `PING_GOOD_MS`-`PING_BAD_MS`, 250-750, and maps that onto `ColorRamp.GetHeatColor`, a smooth green-yellow-orange-red ramp over 0 to 1); the board is drawn between the two bars in its own viewport (`GetBoardViewport`), which also clips it. Over the board's top right corner, just under the score bar, the `MiniMap` control draws the whole map in a yellow-bordered black square with rounded corners (`MiniMap.CORNER_RADIUS`, cut with `RoundedCorners.GetRowInset`) (`MINI_MAP_SCREEN_FRACTION` of the smaller screen side, placed by `GetMiniMapBounds`): no maze, a `#777` (`ClientColors.COLOR_MINI_MAP_WARP`) arch, an upside down U, on every warp door (every `MazeMovement.IsWarpCell` cell, found by `MiniMapMath.GetWarpCells` whenever the map changes; built from `MiniMapMath.IsOnArch`), a team-colored ring on every flag base (found in the map by `MiniMapMath.GetFlagBases`, library, again whenever the map changes; the ring texture is built from `MiniMapMath.IsOnRing`), a team-colored dot for every living pac (10 pixels) and a 15 pixel five-pointed star for the player's own (built from `MiniMapMath.IsOnStar`) (a carrier's dot or star flickers like the flag it carries), a royal purple (`ClientColors.COLOR_MINI_MAP_POWER_UP`) X for every power up, the same 10 pixels as the dots and triangles (built from `MiniMapMath.IsOnCross`), and a triangle pointing up for every flag not being carried (built from `MiniMapMath.IsOnTriangle`; `ClientColors.GetFlagColor`, the same flicker as on the board), positioned by `MiniMapMath.CellToMiniMap` (library). `DrawFlagPointers` draws a `Const.IMAGE_POINTER` (white triangle pointing right, magenta keyed out) for every flag, on screen or off and carried or not (none for a flag right on the player, i.e. one they carry), so with several flags a team has several pointers: tinted `ClientColors.GetTeamColor`, `FLAG_POINTER_PIXELS` wide, always shown (no blinking), at `FlagPointerMath.GetCirclePosition` (where the line from the player, the camera's centre, to the flag crosses a circle around the player whose radius is `FlagPointerMath.GetDistance` from the player to the mini map's bottom left corner) and turned by `FlagPointerMath.GetAngle`. They get their own pass in the board's viewport after the HUD, so they stay off both bars, and the mini map is drawn last of all, over them. Under the mini map, `HUD_MARGIN` below it and as wide (`GetPlayerStateBounds`), the `PlayerState` control shows the player's own power up effect in the same yellow border and rounded black panel (`MiniMap.BORDER_PIXELS`, `CORNER_RADIUS`, filled by `TextureHelper.FillRounded`): "Power Up: " and the effect's name (`PowerUpEffects.GetLabel`, "Power Up: None" in grey when there isn't one) left aligned in JLS Space Gothic 30, over a grey meter (`ClientColors.COLOR_POWER_UP_BAR_EMPTY`) with a yellow bar that shrinks to the left as the time runs out (`ClientGameState.GetOwnPowerUpEffect`, `GetOwnPowerUpFill`, from `PowerUpEffects.GetFill`), the player's own size ("Size n") left aligned under the meter, then a size bar (`SizeBar`, library: `GetFill`, 0 to 1 over 0 to `FULL_SIZE` 100, and `GetLevel`, `eSizeBarLevel` Normal, Big above 100, Huge above `HUGE_SIZE` 150, colored by `ClientColors.GetSizeBarColor`: green, bright orange, bright red), and under that a hunger meter, grey filling red from the left (`COLOR_PAC_RED`) as the pac nears starving (`ClientGameState.GetOwnHungerFill`, from `PacRules.GetHungerFill`: `PacState.MsSinceEaten`, sent in every snapshot, over `GameConfig.MsUntilStarvation`), full while it shrinks and empty again whenever it eats a dot or power pill.
- Flags are tracked by the server as `GameFlag`s (base, position, carrier), made from the map's flag base cells at level start, and sent in `SnapshotMessage.Flags`. The client draws flags only from the snapshot, not from the map. `PacRules` (library) holds the pac size and touch rules both sides use. `GameServer.UpdateFlags` runs pickup, rescue and capture each tick; whatever kills a pac must call `GameServer.DropFlag` first. Flag events are broadcast as `GameEventMessage`s with `Team` set to the flag's team: `DropFlag` sends `FlagLost` for each flag actually let go (carrier killed, left or stepped onto a spawn tile), a rescue sends `FlagReturned`, and a capture sends `FlagCaptured` (team of the captured, enemy flag).
- Game simulation runs in `GameServer.Update` each tick (nothing runs while `GameServer.IsPaused`, which is true when no humans are connected): respawns, `SteerBots`, `MovePacs`, `UpdateEating` (power pill timers, dots, power pills, starvation), `UpdatePacFights`, `UpdateGhosts`, `UpdatePowerUps`, `UpdateFlags`, `UpdateRegens` (power pills only), then one `CellsChangedMessage` for the tick, `CheckAboutToWin` and `CheckLevelWon`. `CheckAboutToWin` broadcasts a `GameEventMessage` `AboutToWin` (with `Team`) the first time in a level a team's score passes `GameServer.ABOUT_TO_WIN_PERCENT` (90) of `MaxScore` (`GameServer.IsAboutToWin`), once per team per level (reset by `StartLevel`), and not for a team that has already won. Points go through `AddScore`, which credits the player (`Player.Score`, reset each level, and `Player.TotalScore`, never reset) as well as the team. When a team wins, `CheckLevelWon` broadcasts a `LevelWonMessage` (winner, team scores, `MsRemaining` and a `PlayerResult` for every player) and starts the intermission: for `GameConfiguration.IntermissionTimeMs` ms `Update` runs only `UpdateIntermission`, then `StartLevel` begins the next level. A player joining during it is sent the `LevelWonMessage` after `LevelStartMessage`. On the client, `ClientGameState.IsIntermission` is true from `LevelWonMessage` to the next `LevelStartMessage`; it keeps each team's results ranked by `PlayerResult.RankTeam` and the countdown (`GetIntermissionSecondsLeft`). `MultiPlayerGameScreen` stops the music, clears the announcer queue, plays `Const.SFX_LEVEL_WON` (a chiptune "Charge!" fanfare) once if the player's own team won or `Const.SFX_LEVEL_LOST` (a chiptune sad trumpet; how both were made is in README.md) if it lost (`Announcements.GetLevelEndSound`, library), and draws `DrawResults` instead of the game, over `Const.IMAGE_WIN_BLUE` or `Const.IMAGE_WIN_RED` for the winning team (scaled to cover the screen): the winner, then each team's score and players in Arial20 split into as many columns as fit (own line in yellow) on its own opaque black panel with rounded corners (`RoundedCorners.GetRowInset`, library) fitted tightly around them (columns as wide as their widest line, sharing the half's width only if they would not fit), and "Next Level in n" (`Const.STRING_NEXT_LEVEL_IN`) near the bottom, with a random loading screen tip (`ClientGameState.IntermissionTip`, in quotes, no panel) under it at the bottom centre. Each step is public so tests call it directly. Movement is `MazeMovement` (library): everything travels along cell centres, turns only at centres, and wraps through warp tunnels. Ghosts can't use the tunnels: `GhostBrain` and the ghost's `MazeMovement.Move` call pass `canWarp: false`, which makes `MazeMovement.IsWarpCell` cells (open cells on the map edge) count as walls. `CanMove`, `Move` and `PathMap.Fill` also take a `blocked` mask of cell flags that count as walls: ghosts use `MazeMovement.GHOST_BLOCKED` (walls and both spawns), pacs `MazeMovement.GetPacBlocked(team)` (walls and the enemy spawn), and bots `PacBrain.GetBlocked`, which adds their own spawn while carrying a flag. A carrier stepping onto a spawn tile drops the flag in the cell it came from (`MovePacs`, `DropFlag(player, x, y)`), and a pac on a spawn tile can't pick a flag up (`GameServer.IsSpawnCell`). Ghost targeting, fleeing from pacs that repel ghosts (`Player.RepelsGhosts`: a power pill, Invincible or Doctor Away), and path finding are `GhostBrain` (library). Every ghost has a `GhostPersonality` (name, color, `eGhostBehavior`, `SpeedScale`, `VisionScale`) from the `GhostPersonalities.ALL` table (21 of them, `Id` = index; `NORM` is today's plain chaser). `MapMaker.PickGhostLineup(config, seed, level)` gives each ghost id its personality for a level, with its own `Random` (salted level seed) so the map doesn't change; the server's `CreateGhosts` and `ClientGameState` (`GhostLineup`) both call it, so nothing is sent. Lineups never repeat a personality except Norm, which fills every slot past the 21; odd levels always have a Norm and even levels draw it `GhostPersonalities.NORM_WEIGHT` (3) times as often. `GameServer.UpdateGhosts` runs each ghost by its behavior: `PickGhostTarget`, `IsGhostStill` (Sleeper, Shy, Lurker), `ChooseGhostDirection` at cell centres and `GetGhostSpeedScale`, built from public `GhostBrain` rules (`PickStubbornTarget`, `PickFlagHoundTarget`, `PickSmallest`, `PickBiggest`, `PickGrudgeTarget`, `PickRandomTarget`, `FindNearestPac`, `GetAmbushCell`, `ShouldScatter`, `FindHomeCorner`, `IsOutsideLeash`, `UpdateAttention`, `FindLurkJunction`, `GetFrenzySpeedScale`, `RecordTargetCell`/`GetLaggedCell`, `ChooseStraightLineDirection`, `IsFacedBy`, `GetMimicDirection`, `IsNapping`, `FindLeader`; their tuning constants are on `GhostBrain`). Per-ghost state for them is on `Ghost` (`SpawnCell`, `HomeCell`, `GrudgeId`, `LifeMs`, `LurkCell`, `TargetHistory`…), reset by `SpawnGhost` except the grudge. Fleeing a threat always comes first. To add a personality, add an `eGhostBehavior` value and a row to `GhostPersonalities.ALL` (unique name and color, clear of the team hues; `GhostPersonalityTests` checks), handle it in `GameServer`, and add it to the table in Specs.md. Size, speed and contact rules are in `PacRules` (`PacRules.START_SIZE`, 0, is also the smallest a starving pac gets). Pacs never explode. Dots add `DotSizeGain` up to `PacMaxSize`; a power pill is a power up effect. A pac has at most one power up effect (`ePowerUpEffect`, `Player.PowerUpEffect`, with the ms left in `Player.PowerUpMs`), and every effect lasts `GameConfig.PowerUpDurationMs` (default 10000): `GameServer.StartPowerUpEffect` ends a different effect first (`EndPowerUpEffect`) and restarts the timer, so the same effect again only restarts it, and `UpdateEating` counts it down and calls `EndPowerUpEffect` when it runs out. A power pill (`ePowerUpEffect.PowerPill`, `Player.IsPowered`) adds `PowerPillSizeGain` (past `PacMaxSize` if need be) when it starts and takes it away when it ends (`PacRules.WearOffPowerPill`). Both are sent in `PacState.PowerUpEffect` and `PowerUpMsLeft` (`PacState.Powered` is the pill). Item effects go through `StartPowerUpEffect` too, from `ApplyPowerUp`; give each new effect an `ePowerUpEffect` value and a name in `PowerUpEffects.GetName` (library), and a speed scale in `PacRules.GetEffectSpeedScale` if it changes speed (or a dot gain scale in `PacRules.GetDotGainScale` if it changes growth). Only a powered pac of at least `PacMaxSize` kills ghosts (`PacRules.CanKillGhost`); a starving pac loses `PacShrinkPerSecond` each second, and `MovePacs` and `SteerBots` move each pac at `PacRules.GetSpeed` (`PacSpeed` at size 0, 20% faster at `PacMaxSize`). Each pac's `Eating` (in `PacState`) is set whenever it enters a new cell, to whether that cell had a dot or power pill; the client loops `Const.SFX_EAT` while its own pac is eating and `Const.SFX_SIREN` while its own pac is alive and not eating (`ClientGameState.IsOwnPacNotEating`), neither during the intermission. It also loops `Const.SFX_POWER_PILL` while its own pac has a power pill working (`ClientGameState.IsOwnPacPowered`). Eaten cells are `CellRegen`s; a player who joins mid-level is sent them (`BuildEatenCells`) after `LevelStartMessage`.
- Action button: space (or gamepad A) in a game makes `MultiPlayerGameScreen` send an `ActionMessage` (no fields); the server runs `GameServer.HandleAction(player)`, which does whatever the living pac's buff does on action (a switch on `PowerUpEffect`). Buffs that act on the button add a case there and set `acted` when the press did something; then the button does nothing for `WeaponRules.ACTION_COOLDOWN_MS` (500, `Player.ActionCooldownMs`, counted down in `UpdateWeaponEffects`), whatever the effect.
- Turn assist (human pacs only; bots and ghosts turn exactly): `TurnAssist` (library). On an `InputMessage` with a direction, `GameServer.BufferTurn` keeps it in `ServerPlayer.BufferedTurn` for `GameConfig.TurnBufferTimeMs` ms (default 400) and sets `HasNewTurnRequest`. In `MovePacs` the wanted way is `TurnAssist.GetWantedTurn` (held, else the buffered one while it lasts); on a new press `TurnAssist.TryLateTurn` puts a pac that has just passed an open junction back on its centre facing the new way, and `Move` gets the distance back. The window is `TurnAssist.GetGraceDistance`: `GameConfig.TurnGraceDistance` (cells, default 0.3) plus the pac's speed times its lag (capped at `GameConfig.LagCompensationMaxMs` ms, default 250), at most `TurnAssist.MAX_GRACE_CELLS` (0.9), and never more than `ServerPlayer.StraightDistance` (cells moved since its last change of direction). The buffer clears once the pac faces that way or runs out. Lag is measured by the server: `UpdateLagPings` sends each human a `ServerPingMessage` (`ServerTime` from `GameServer.ClockMs`) every `LagEstimate.PING_INTERVAL_MS` (1000), the client answers at once with a `ServerPongMessage` (`MultiPlayerGameScreen.ReceiveMessages`), and the round trip goes into `ServerPlayer.Lag` (`LagEstimate`, a running average moving `SMOOTHING` of the way to each sample). Each of the three settings is 0 for off; `ConfigManager.Load` clamps them. The client's own Ping/Pong for the stats bar is separate.
- Power ups: `GameServer.UpdatePowerUps` counts the level's play time (`PowerUpTimerMs`, reset with the power ups by `StartLevel`) and calls `SpawnPowerUp` each time it passes a multiple of `GameConfig.PowerUpSpawnTimerMs` (ms, default 30000, 0 or less for none; `PowerUpRules.GetSpawnsDue`). A `PowerUp` (library, a `GameEntity` with `Item` and `Exit`) starts on a random `PowerUpSpawns` cell with a random item from the level's set (`PowerUpRules.PickItem`) and heads for a random warp exit (`PowerUpRules.FindExits`, `MazeMovement.IsWarpCell`). `PowerUpRules.Move` steps it downhill at `PowerUpRules.SPEED` (3 cells/s) on the exit's full `PathMap`, built once per level per exit, blocked only by walls (`PowerUpRules.BLOCKED`), so it crosses spawn tiles; on reaching the exit's centre it is removed. Any living pac touching one (`PowerUpRules.IsTouching`) eats it: it is removed, a `GameEventMessage` `PowerUpEaten` (actor the pac, target the power up's id) is broadcast and `GameServer.ApplyPowerUp(player, item)` runs, which starts the item's effect. Weapons: `GameServer` keeps `_WeaponEffects` (`WeaponEffect`, library, a `GameEntity` with `Kind` (`eWeaponEffect`), `OwnerId`, `OwnerClear`, `CapturedGhostId`), updated by `UpdateWeaponEffects` after `UpdateGhosts`, cleared by `StartLevel`, and sent in `SnapshotMessage.WeaponEffects` (`WeaponEffectState`); the client draws them in `DrawWeaponEffects` (after the power ups, flames first, the sword turned by `WeaponEffectSprites.GetRotation`). Speeds, limits and target picking are in `WeaponRules` (library). White Sword (`SwordSwing`) and Fire Flower (`FireFlower`) act on the action button in `HandleAction`: a sword (at most `MAX_SWORDS` 2 per pac, 2 times PacSpeed) or a fireball (as many as you like, 1.25 times PacSpeed); both fly straight with `MazeMovement.Move` (walls stop them) and `HitFirstThing` kills the first pac (any team; the owner once `OwnerClear`) or ghost they touch unless invincible (`KillPacBy`, `KillGhost` credit the owner only for enemies and ghosts). - Bots: `GameConfiguration.MinPlayers` sets how many players the server keeps; `GameServer.BalanceBots` adds or removes bots (counts and teams from `BotPlanner`) at startup and after every join and leave. With `ServerSettings.AutoBalanceTeams` (server.cfg, default true) it instead gives each team the bots `BotPlanner.GetBalancedBotCounts` asks for, so both teams are always the same size, however many bots that takes; a joining human only replaces a bot on their preferred team. `TeamBalancer.AssignTeam` puts an Either player on the smaller team, and the server keeps each player's choice in `ServerPlayer.PreferredTeam` for rebalancing between levels. Server tests that expect no bots set `AutoBalanceTeams = false`. A bot is a `ServerPlayer` with no `Connection` (`IsBot`) and an id from `GameServer.BOT_ID_BASE` up; `Broadcast` skips bots, and `PlayerCount` counts humans only. `GameServer.SteerBots` sets each bot's `Input` from `PacBrain.ChooseDirection` (library) when it reaches a cell centre, before `MovePacs`, and turns it back mid-cell when `PacBrain.ShouldTurnBack` (at most once per `BotMemory.TURN_BACK_COOLDOWN_MS`, 500). Bots remember between centres in `ServerPlayer.Memory` (`BotMemory`, library; `SteerBots` counts its timers down with `Update`, and it is `Reset` when the bot dies and at `StartLevel`). Goals are `eBotGoal`, in priority order: `PacBrain.PickGoal` picks one and `FindGoalTarget` finds its target cell (`PickTarget` is `PickGoal`'s target). Power pills (`POWER_PILL_DISTANCE`, 15) come right after chasing carriers, before power ups and hunting. An invincible bot (`Player.IsInvincible`) uses `INVINCIBLE_GOAL_ORDER` (chase mode: carriers, pacs, ghosts out to `SEARCH_DISTANCE`, then rescue, enemy flag, dots; no power pills or power ups, and plain dots only, since either would replace the effect), a rescue doesn't interrupt it, `IsThreat` is false for it and `IsPrey` true for every enemy that isn't invincible, and an invincible enemy is a threat to every other bot; `PacBrain.CanKillGhosts` (power pill at full size, or invincible) replaces `PacRules.CanKillGhost` in the brain. A goal is kept for a random `GOAL_COMMIT_MIN_MS` to `GOAL_COMMIT_MAX_MS` (2 to 4 s, `BotMemory.IsCommitted`), and dropped sooner only when its target is gone or `PacBrain.InterruptsGoal` (picked up or lost a flag, own flag to rescue). Fleeing starts at `DANGER_DISTANCE` (5) but carries on while a threat is within `PacBrain.CALM_DISTANCE` (8) or `BotMemory.FLEE_MIN_MS` (1000) hasn't passed (from the remembered `ThreatCells`); when it stops, `BotMemory.StopFleeing` drops the goal and for `AVOID_MS` (3000) marks the cells within `AVOID_RADIUS` (2) of the threats in `AvoidMask`, which `PathMap.Fill` (its `avoid` mask) keeps the target search out of, never the threat search. A kept goal whose target can't move (`PacBrain.IsMovingTarget` false) never makes the bot turn back; it wanders on instead. `ChooseDirection` with no memory remembers nothing, as tests of single choices expect. So bots don't move in lockstep, `ChooseDirection` wanders instead of heading for its target `PacBrain.RANDOM_TURN_PERCENT` (15) of the time, never while fleeing or carrying a flag (tests pass `randomTurnPercent: 0` for exact choices). Bots misjudge other pacs' sizes: `IsThreat` and `IsPrey` compare against `PacBrain.GetPerceivedSize`, the real size plus up to `SIZE_PERCEPTION_ERROR` (0.1) of `MaxSize` either way, from `GetPerceptionError(seed, observerId, otherId)` (a hash, so it's fixed per pair) seeded by `BotWorld.PerceptionSeed`, which the server sets to the level's map seed. The brain sees a `BotWorld` and searches with `PathMap` (breadth-first, warp-aware, buffers reused) out to `PacBrain.SEARCH_DISTANCE` steps; anything further is a flag base, reached by stepping downhill on the full `PathMap` the server builds for each base at level start (`BotWorld.FlagBasePaths`; one set each for red bots, blue bots and carriers, since their blocked cells differ, picked per bot by `GameServer.GetBasePaths`). Keep bot searches bounded: a full-map search costs about 1 ms, and there can be over 100 bots. `GameFlag` is in the library so the brain can see flags. Clients aren't told who is a bot.
- `NetworkLoopbackTests` run a real `NetworkServer` and `NetworkClient` on 127.0.0.1 with a free port, so they need no firewall approval.

## Workflow

- Build everything: `dotnet build EatMe.sln`
- Run the server: `dotnet run --project EatMeServer`
- Run the tests: `dotnet test EatMeTests`
- For quick testing, `StartServer.bat` and `StartClient.bat` in the solution root run the published builds in `publish\server` and `publish\client`, so run `PublishApps.bat` first. Each starts in its exe's folder so `server.cfg`, `LoadingScreenTips.txt` and content are found.
- `PublishApps.bat` in the solution root publishes Release builds of the client and server to `publish\client` and `publish\server` (win-x64, framework-dependent so players need the .NET runtime, no `.pdb` files), deleting those folders first.
